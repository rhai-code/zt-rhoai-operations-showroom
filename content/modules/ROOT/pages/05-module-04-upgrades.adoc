== Learning Objectives

By the end of this module you will be able to:

* Describe the RHOAI release cadence and life cycle support policy
* Inspect operator subscriptions, installed versions, and available update channels using OLM
* Describe the rhods-operator meta-operator model -- the ODH managed components it owns versus the external prerequisite operators it depends on, and the upstream to midstream to product flow
* Explain the differences between manual and automatic approval strategies
* Demonstrate operator pinning to prevent unintended dependent operator upgrades
* Describe MaaS upgrade considerations across RHOAI 3.4, 3.5, and 3.6
* Create a pre-upgrade checklist and understand rollback limitations

[IMPORTANT]
====
We apply the manifests manually to the cluster in this exercise so we can see the changes and learn the process. In a production environment, you would use GitOps to apply the manifests to the cluster. We do not practice what we preach as far as GitOps in this workshop.
====

The exercises in this module are **walkthrough-style**. You will inspect and plan upgrade operations but will **not execute an actual upgrade** on the cluster. The goal is to build the skills and confidence to perform upgrades in your own environments.

=== Life Cycle Support

RHOAI follows the https://access.redhat.com/support/policy/updates/openshift[Red Hat OpenShift product life cycle]: a time-delineated, phased life cycle in which at least four OpenShift minor versions are supported at any time, with releases forecast on a four-month cadence. All released errata remain accessible to active subscribers across the entire life cycle. For RHOAI itself, the current minor release and the previous one receive full support; older releases move to maintenance and then end of life.

image::ocp-lifecycle-phases.png["OpenShift v4 life cycle phases -- Full Support, Maintenance Support, and Extended Update Support add-on terms across even-numbered EUS releases", width=100%]

[cols="1,2,3"]
|===
|Phase |Duration |What you get

|**Full Support**
|Begins at GA of the minor version; ends after 6 months OR 90 days after the GA of the superseding minor release, whichever is later
|Qualified Critical, Important, and Moderate CVEs (RHSAs) and urgent/selected high-priority bug fixes released as they become available; other fixes via periodic updates. Customers are expected to run the latest z-stream (4.x.z) to receive fixes.

|**Maintenance Support**
|After Full Support; ends 18 months after GA
|Security fixes only (qualified RHSA CVEs) plus urgent/selected bug fixes at Red Hat's discretion. After the phase ends, software and documentation remain available but no technical support is provided except assistance to upgrade to a supported version.

|**Extended Update Support (EUS) Add-Ons**
|Optional add-on terms for even-numbered minor releases (for example, 4.14, 4.16)
|Term 1 (6 months) plus Terms 2 and 3 (12 months each) extend the same release for up to 36--48 months, with technical support and backports of security and urgent bug fixes for platform-aligned operators. Included with Premium subscriptions; optional add-on for Standard.
|===

[NOTE]
====
Always check the https://access.redhat.com/support/policy/updates/openshift[OpenShift Container Platform Life Cycle] page for the current support matrix. Support timelines may shift with the release cadence.
====

== Exercise 3: Inspect Dependent Operator Subscriptions

. List All Operator Subscriptions. View all operator subscriptions across the cluster to identify RHOAI dependencies:
+
[source,bash,role="execute"]
----
oc get subscriptions -A -o custom-columns='NAMESPACE:.metadata.namespace,NAME:.metadata.name,CHANNEL:.spec.channel,APPROVAL:.spec.installPlanApproval,CSV:.status.installedCSV'

. Understand the rhods-operator as a Meta Operator. The rhods-operator does not implement the RHOAI components itself. It deploys and reconciles component controllers built from the Open Data Hub (ODH) upstream and manages two distinct kinds of dependencies:
+
[cols="1,3"]
|===
|Dependency |What it means

|**ODH Managed Components**
|What the operator *owns*: the dashboard, workbenches, data science pipelines, KServe, model registry, the Kueue integration, TrustyAI, Ray, hardware profiles, and the MaaS auth/gateway APIs. Each component is exposed through the DataScienceCluster (DSC) `spec.components` API with a `managementState` (`Managed`, `Removed`, or `Unmanaged`), reconciled by a dedicated controller inside the operator, with component workloads deployed into the `redhat-ods-applications` namespace (the DSCI `spec.applicationsNamespace`).

|**Prerequisite Operators (External)**
|What the operator *depends on but does not manage*: OpenShift Serverless (Knative -- serverless KServe mode only), RHCL/Kuadrant (MaaS gateway and auth), Node Feature Discovery, and the NVIDIA GPU Operator. Administrators install these separately; the operator needs each one only when the corresponding component is enabled.
|===
+
The relationship to upstream, midstream, and the product:
+
[cols="1,3"]
|===
|Layer |What it is

|**Upstream**
|The Open Data Hub (ODH) community project -- provides the operator and the component implementations.

|**Midstream**
|Red Hat's staging fork of the ODH operator, where upstream content is pinned, patched for the product (the DSC/DSCI APIs, RHCL integration), built, and tested.

|**Downstream (product)**
|The tested CSV ships in the `redhat-operators` catalog as `rhods-operator`, managed by OLM -- the operator this module upgrades.
|===
+
[NOTE]
====
The upstream lineage is visible on the cluster: every CRD the operator owns uses the `opendatahub.io` domain (for example, `datascienceclusters.datasciencecluster.opendatahub.io`). Operational consequences: one CSV bundles *all* managed components, so the subscription channel pins the whole stack while the external prerequisite operators upgrade independently (the pinning risk demonstrated in Exercise 4); and the DSC/DSCI custom resources are the declarative GitOps knobs for the stack -- manage those in git rather than the component workloads the operator deploys.
====

== Exercise 4: Demonstrate Manual Approval Strategy and Operator Pinning

. Understand Approval Strategies. OLM supports two install plan approval strategies:
+
[cols="1,3"]
|===
|Strategy |Behavior

|**Automatic**
|OLM automatically approves and installs any update that appears in the subscribed channel. No human intervention required. Risk: unplanned upgrades.

|**Manual**
|OLM creates an InstallPlan but does not approve it. An administrator must explicitly approve the plan before the upgrade proceeds. Benefit: full control over timing.
|===

. View Pending Install Plans. Check whether any install plans are waiting for approval:
+
[source,bash,role="execute"]
----
oc get installplan -A -o custom-columns='NAMESPACE:.metadata.namespace,NAME:.metadata.name,CSV:.spec.clusterServiceVersionNames[*],APPROVED:.spec.approved,PHASE:.status.phase' | grep -v "^NAMESPACE" | sort
----

. Demonstrate Switching to Manual Approval (Dry Run).
+
[CAUTION]
====
Do **not** execute this command on the shared cluster. It is shown here for reference. Switching a running operator to Manual approval on a shared cluster could block critical security patches.
====
+
To switch the RHOAI operator from Automatic to Manual approval, you would patch the subscription:
+
[source,yaml]
----
# DO NOT APPLY -- reference only
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: rhods-operator
  namespace: redhat-ods-operator
spec:
  channel: stable-3.5
  installPlanApproval: Manual     # <1>
  name: rhods-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
----
<1> Changed from `Automatic` to `Manual`

. Switch and approve via the CLI (reference only). The equivalent `oc patch` command:
+
[source,text]
----
# DO NOT EXECUTE on shared cluster
oc patch subscription rhods-operator -n redhat-ods-operator \
  --type merge \
  -p '{"spec":{"installPlanApproval":"Manual"}}'
----
+
After switching to Manual, when a new version appears you would approve the install plan:
+
[source,text]
----
# DO NOT EXECUTE on shared cluster
oc patch installplan <install-plan-name> -n redhat-ods-operator \
  --type merge \
  -p '{"spec":{"approved":true}}'
----
+
[NOTE]
====
Manual approval is a function of the OperatorGroup's namespace, not of a single operator: installing one operator with `installPlanApproval: Manual` causes ALL operators in that namespace to function with the Manual approval strategy, and OLM binds the upgrades of subscriptions sharing a namespace into a single InstallPlan. This is one of the main reasons for giving each operator (or tightly coupled group) its own namespace instead of the shared `openshift-operators` -- the approval strategy, RBAC, and upgrade lifecycle stay isolated. The lab cluster demonstrates both patterns: the RHOAI operator's subscription is alone in the dedicated `redhat-ods-operator` namespace, while the RHCL/Kuadrant dependencies (`rhcl-operator`, `authorino-operator`, `limitador-operator`, `kueue-operator`) share the global `openshift-operators` namespace -- switching any one of them to Manual changes the strategy for all of them. OLM v1 (the Operator Controller) replaces the Subscription/OperatorGroup/InstallPlan model with per-operator ClusterExtensions, each with its own upgrade policy, removing this shared-namespace entanglement.
====

. Operator Pinning: The RHCL Example. Operator pinning prevents a dependent operator from upgrading beyond a tested version. This is critical for operators like RHCL where a minor version bump could introduce breaking API changes.
+
**Why pin RHCL?**
+
RHOAI 3.5 is tested against a specific RHCL version. If RHCL auto-upgrades to a newer release, the Kuadrant/Authorino integration may break, causing inference endpoint authentication failures.
+
**Pinning strategy:** **Pin the subscription channel** to a specific minor version (e.g., `stable-1.1` instead of `stable`), **set Manual approval** as a safety net even within the pinned channel, and **test before approving** any install plan in a staging environment. For example, an RHCL subscription pinned to a specific channel:
+
[source,yaml]
----
# Example RHCL subscription pinned to a specific channel
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: connectivity-link-operator
  namespace: openshift-operators
spec:
  channel: stable-1.1              # <1>
  installPlanApproval: Manual       # <2>

== Conceptual Section: Minor Version Upgrade Workflow

This section walks through the process of upgrading RHOAI from one minor version to the next (e.g., 3.4 to 3.5). You will not execute these steps, but you should understand each one.

=== Upgrade Sequence

A minor version upgrade follows this sequence:

[arabic]
. **Read the release notes** of the version you are intending on upgrading to -- identify breaking changes, deprecated features, and new prerequisites
. **Pre-upgrade checks** (see checklist below)
. **Upgrade dependent operators** to RHOAI-tested versions
. **Switch the RHOAI subscription channel** from `stable-3.4` to `stable-3.5`
. **Approve the install plan** (if using Manual approval)
. **Monitor the upgrade** via CSV status and pod rollouts
. **Post-upgrade validation** of all RHOAI components

[NOTE]
====
You can delete the operator but not the operands: uninstalling the operator (subscription + CSV) removes its controllers but leaves every operand in place -- the DataScienceCluster, DSCInitialization, workbenches, InferenceServices, model registries, and their data all survive, and reinstalling the operator re-adopts them. This is common to most operators: the operator owns the controllers, the operands are ordinary API resources. Operationally this cuts both ways during an upgrade -- a failed operator rollout does not delete user workloads, but a broken operand state also survives an operator reinstall, so it may need explicit repair.
====

=== Channel Switch

The channel switch is the trigger for a minor version upgrade:

[source,yaml]
----
# Example: switching from 3.4 to 3.5
# DO NOT APPLY on the shared cluster
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: rhods-operator
  namespace: redhat-ods-operator
spec:
  channel: stable-3.5          # <1>
  installPlanApproval: Manual
  name: rhods-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
----
<1> Changed from `stable-3.4` to `stable-3.5`

=== Monitoring the Upgrade

After approving the install plan, monitor the rollout:

[source,text]
----
# Watch CSV transition (do not run -- reference only)
watch oc get csv -n redhat-ods-operator

# Watch component pods restart
watch oc get pods -n redhat-ods-applications

# Check DataScienceCluster health
watch oc get datasciencecluster -A -o jsonpath='{.items[0].status.phase}'
----

The upgrade is complete when:

* The new CSV shows `Phase: Succeeded`
* All pods in `redhat-ods-applications` are in `Running` state
* The DataScienceCluster shows `Phase: Ready`

== Conceptual Section: MaaS Version Differences (3.4 to 3.5 to 3.6)

Model-as-a-Service (MaaS) is the managed inference offering within RHOAI. Its architecture has evolved significantly across recent releases.

=== Version Comparison

[cols="1,2,2,2"]
|===
|Aspect |RHOAI 3.4 |RHOAI 3.5 |RHOAI 3.6 (projected)

|**Serving stack**
|KServe + vLLM (single-model)
|KServe + llm-d GA (distributed)
|KServe + llm-d + Praxis.fast runtime

|**Routing**
|Istio / Service Mesh gateway
|EPP (KV-cache-aware)
|Enhanced EPP with session affinity

|**API Gateway**
|Service Mesh + 3scale (optional)
|RHCL / Kuadrant (replaces 3scale)
|RHCL with per-model rate limits

|**Metering**
|Not available
|External metering (Dev Preview)
|Full metering integration with cost attribution

|**Multi-tenancy**
|Namespace isolation only
|Namespace + RBAC-scoped model access
|Hierarchical tenancy with project groups

|**Autoscaling**
|HPA on CPU/memory
|KPA + HPA with custom GPU metrics
|Predictive autoscaling (TP)

|**MIG support**
|Static MIG only
|Static + Dynamic MIG
|Dynamic MIG + DRA scheduling
|===

=== Upgrade Considerations for MaaS

When upgrading a cluster that runs MaaS workloads, pay special attention to:

[arabic]
. **Inference downtime**: Model serving endpoints may be briefly unavailable during the operator upgrade. Plan a maintenance window.

. **RHCL version coupling**: The API gateway configuration format may change between versions. Test RHCL + RHOAI version combinations in staging.

. **EPP configuration migration**: EPP routing policies from 3.4 are not automatically migrated to the 3.5 format. Review the migration guide in the release notes.

. **vLLM to llm-d migration**: Models deployed with standalone vLLM in 3.4 should be migrated to llm-d InferenceServices in 3.5 for ongoing support.

. **Metering data**: The metering schema changes between 3.5 Dev Preview and 3.6 GA. Export metering data before upgrading if you need historical records.

=== Rollback Considerations

[WARNING]
====
OLM does **not** support automatic operator rollback. Once an operator upgrade completes, the previous CSV is removed. Rollback requires manual intervention and is not guaranteed to work.
====

**What rollback options exist:**

[cols="1,3,1"]
|===
|Option |Description |Reliability

|**OADP restore**
|Restore operator namespace from a pre-upgrade OADP backup. Restores CRDs, deployments, and custom resources.
|Medium -- may conflict with cluster state

|**Reinstall previous version**
|Uninstall the operator, clean up CRDs, and reinstall the previous version from its channel. Data loss risk for any resources managed by the operator.
|Low -- data loss likely

|**Channel rollback**
|Switch the subscription back to the previous channel (e.g., `stable-3.5` back to `stable-3.4`). Only works if OLM has not garbage-collected the old CSV bundle.
|Very low -- rarely works in practice

|**Cluster restore**
|Restore the entire cluster from an infrastructure backup (etcd snapshot). Reverts everything, not just the operator.
|High -- but reverts all changes
|===

**Best practice:** Treat RHOAI upgrades as one-way operations. Invest in pre-upgrade testing in staging environments rather than relying on rollback.

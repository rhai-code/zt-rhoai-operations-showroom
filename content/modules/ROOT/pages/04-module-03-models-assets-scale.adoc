== Exercise 2: Build a ModelCar OCI Container

A ModelCar is a lightweight OCI container image that packages model weights and metadata for deployment. KServe can pull model artifacts directly from an OCI registry, avoiding the need for S3 storage in some deployments.

. Create the model artifacts. A ModelCar packages the serialized model artifact, not the training
  code. In a real workflow you would train in a workbench (for example the custom image from
  Exercise 1, which has scikit-learn) and export a pickle of the trained model. The bastion does
  not have scikit-learn, so this exercise creates the artifact with the Python standard library --
  KServe pulls the artifact out of the OCI image without unpickling it, so the packaging workflow
  is what matters:
+
[source,bash,role="execute",subs="specialcharacters,attributes"]
----
mkdir -p $HOME/modelcar-{guid}/model
python3 -c "
import pickle
model = {'algorithm': 'RandomForestClassifier', 'n_estimators': 10, 'dataset': 'iris', 'accuracy': 0.9667}
with open('$HOME/modelcar-{guid}/model/model.pkl', 'wb') as f:
    pickle.dump(model, f)
print('Model artifact saved.')
"
----

  because it only needs to contain the model artifacts -- no runtime is required:
+
[source,bash,role="execute",subs="specialcharacters,attributes"]
----
cat > $HOME/modelcar-{guid}/Dockerfile <<'EOF'
FROM scratch

COPY model/ /models/iris-classifier/

LABEL org.opencontainers.image.title="iris-classifier-modelcar" \
      org.opencontainers.image.description="Iris RandomForest classifier packaged as ModelCar" \
      org.opencontainers.image.version="1.0.0" \
      ai.kserve.modelcar="true"
EOF

  --from-dir=$HOME/modelcar-{guid} \

  -n {project_name}

. Create the serving runtime. RHOAI 3.5 ships no classic serving runtimes (the sklearn/xgboost
  runtimes from earlier releases are gone) -- the MLServer runtime ships as a template instead.
  Process the template into your project to create the project-scoped `ServingRuntime`:
+
[source,bash,role="execute",subs="specialcharacters,attributes"]

[source,bash,role="execute",subs="specialcharacters,attributes"]

  image as its storage source. Three things are RHOAI 3.5-specific here: the runtime is the
  `mlserver-runtime` ServingRuntime created above; the `modelClass` label tells the MLServer
  runtime which model implementation to load; and the `MLSERVER_MODEL_URI` override points at the
  model file inside the mounted OCI image -- the image volume keeps the image's `/models/` layout,
  and the default injected URI is the `/mnt/models` directory, which the runtime rejects:
+
[source,bash,role="execute",subs="specialcharacters,attributes"]
----
cat <<EOF | oc apply -f -
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: iris-modelcar
  namespace: {project_name}
  annotations:
    serving.kserve.io/deploymentMode: RawDeployment
  labels:
    modelClass: mlserver_sklearn.SKLearnModel
spec:
  predictor:
    model:
      modelFormat:
        name: sklearn
      runtime: mlserver-runtime
      storageUri: "oci://image-registry.openshift-image-registry.svc:5000/{project_name}/iris-modelcar:1.0"
      env:
        - name: MLSERVER_MODEL_URI
          value: /mnt/models/iris-classifier/model.pkl
      resources:
        requests:
          cpu: "500m"
          memory: "512Mi"
        limits:
          cpu: "1"
          memory: "1Gi"
EOF
----

[NOTE]
====
The `storageUri` uses the `oci://` protocol prefix, which tells KServe to pull model artifacts from an OCI container image rather than from S3 or PVC storage. This is the ModelCar pattern -- in RHOAI 3.5 the OCI image is mounted directly into the predictor pod as a Kubernetes image volume, with no storage-initializer init container.
====

== Conceptual Section: Kueue GPU Scheduling

[NOTE]
====
This section is conceptual. The lab cluster does not have GPUs, so you will inspect Kueue and manage its queues -- not run GPU workloads. The full hands-on treatment (simulated GPUs, a booking app, workload admission, preemption) is the separate GPU Resource Management workshop. Kueue itself is real on this cluster: the Red Hat build of Kueue is installed via its OLM operator, so everything you inspect below exists.
====

=== What Is Kueue?

Kueue is a Kubernetes-native job queuing system that manages resource quotas, fair sharing, and workload preemption. In RHOAI, Kueue is essential for managing GPU access across teams and projects: teams submit work to queues, Kueue decides when work admits, and preemption rules decide whose work yields when quota is reclaimed.

Kueue operates through five key CRDs:

[cols="1,3"]
|===
|CRD |Purpose

|**ResourceFlavor**
|Defines a type of resource (e.g., `nvidia-a100-40gb`, `nvidia-l4`, `cpu-only`). Maps to node labels so Kueue knows which nodes provide which hardware.

|**ClusterQueue**
|A cluster-scoped queue that defines resource quotas. Specifies how many resources of each flavor are available and borrowing limits.

|**LocalQueue**
|A namespace-scoped queue that points to a ClusterQueue. Users submit workloads to a LocalQueue; Kueue routes them to the backing ClusterQueue.

|**Cohort**
|A logical grouping of ClusterQueues -- optionally holding its own quota -- whose members can borrow from each other. Enables cross-team resource sharing with guaranteed minimums.

|**Workload**
|The queueing representation of a submitted job. Kueue admits, queues, and preempts Workloads; a job's pods only start once its Workload is admitted.
|===

=== Borrowing vs Reclaiming

Two concepts make shared pools work:

**Borrowing**: a ClusterQueue uses quota from another ClusterQueue in the same Cohort when its own quota is exhausted. The borrower gets extra capacity it does not own.

**Reclaiming**: the queue that owns the quota takes it back from a borrower -- by *preempting* the borrower's workloads when the owner needs its resources.

In short: borrowing is "can I use your unused quota?", reclaiming is "I need my quota back."

=== Preemption Policies

A ClusterQueue's `preemption` block decides what it may evict:

[cols="2,3"]
|===
|Policy |Meaning

|`withinClusterQueue: LowerPriority`
|Evict lower-priority workloads *within the same queue* to admit a higher-priority one.

|`reclaimWithinCohort: Any`
|Preempt workloads that are borrowing from the Cohort, to take owned quota back. Only meaningful with a non-zero `nominalQuota` -- with zero quota there is nothing to reclaim.

|`borrowWithinCohort: LowerPriority`
|While borrowing from the Cohort, preempt *other borrowers* with lower priority -- useful for urgent unreserved work. `Never` means the queue never preempts to borrow.
|===

=== The Cohort Model and Additive Quotas

The full GPU lab configures Kueue in a flat Cohort model:

[source,text]
----
Cohort: unreserved
├── ClusterQueue: unreserved          (borrows from cohort, no preemption rights)
├── ClusterQueue: unreserved-priority (can preempt low-priority borrowing workloads)
├── ClusterQueue: user-alice          (protected nominalQuota, can reclaim from cohort)
└── ClusterQueue: user-bob            (protected nominalQuota, can reclaim from cohort)
----

A critical detail of Kueue's design: Cohort resources are *additive* to ClusterQueue resources -- total capacity = the sum of the ClusterQueue `nominalQuota` values **plus** the Cohort's `nominalQuota`. Quotas do not overlap; they stack. If an unreserved ClusterQueue also had a non-zero nominalQuota, it would be added on top and inflate the total beyond the cluster's real capacity. That is why the GPU lab keeps every unreserved queue at zero nominal and puts the real capacity exclusively in the Cohort: the booking app shrinks the Cohort by exactly the reserved amount when a user reserves a GPU, which is what triggers preemption of unreserved work.

=== Example: ResourceFlavor for GPU Nodes

On a GPU-equipped cluster, a ResourceFlavor would look like this:

[source,yaml]
----

  name: nvidia-a100-40gb

  nodeLabels:
    nvidia.com/gpu.product: "NVIDIA-A100-SXM4-40GB"
  tolerations:
    - key: nvidia.com/gpu

=== Example: ClusterQueue with Quotas and Borrowing

A ClusterQueue defines the total resources available and the borrowing policy:

[source,yaml]
----
apiVersion: kueue.x-k8s.io/v1beta2
kind: ClusterQueue
metadata:
  name: data-science-team
spec:
  cohortName: "research-department"    # <1>
  resourceGroups:
    - coveredResources: ["cpu", "memory", "nvidia.com/gpu"]
      flavors:
        - name: nvidia-a100-40gb
          resources:
            - name: "nvidia.com/gpu"
              nominalQuota: 4           # <2>
              borrowingLimit: 2          # <3>
            - name: "cpu"
              nominalQuota: 32
            - name: "memory"
              nominalQuota: 128Gi
  preemption:
    withinClusterQueue: LowerPriority
    reclaimWithinCohort: Any
----
<1> Cohort membership enables borrowing from other ClusterQueues in the same cohort
<2> Guaranteed quota: 4 GPUs always available to this team
<3> Can borrow up to 2 additional GPUs from the cohort when other teams have idle resources

== Conceptual Section: MIG, Dynamic MIG, and DRA

[NOTE]
====
This section describes GPU partitioning technologies. These concepts are important for planning RHOAI deployments but cannot be demonstrated on a CPU-only cluster.
====

=== Multi-Instance GPU (MIG)

NVIDIA Multi-Instance GPU (MIG) allows a single physical GPU to be partitioned into up to seven isolated instances, each with its own memory, cache, and compute resources.

[cols="1,2,2"]
|===
|MIG Profile |GPU Memory |Use Case

|`1g.5gb`
|5 GB
|Small inference workloads, notebook exploration

|`2g.10gb`
|10 GB
|Medium model training, batch inference

|`3g.20gb`
|20 GB
|Large model fine-tuning

|`4g.20gb`
|20 GB
|Higher compute, same memory as 3g

|`7g.40gb`
|40 GB (full GPU)
|Full GPU for largest workloads
|===

MIG provides hardware-level isolation -- each instance has guaranteed memory bandwidth and compute, unlike time-slicing which shares resources.

=== Dynamic MIG

Dynamic MIG (available through the NVIDIA GPU Operator) enables on-the-fly reconfiguration of MIG partitions based on workload demand. Key benefits:

* **Automatic partitioning**: The GPU Operator watches for pod resource requests and reconfigures MIG profiles to match
* **No node drain required**: Partitions are adjusted without evicting existing workloads (when possible)
* **Strategy-based**: Administrators define a `MIGStrategy` (e.g., `mixed` or `single`) on the ClusterPolicy

=== Dynamic Resource Allocation (DRA)

DRA is a Kubernetes-native mechanism (GA in Kubernetes 1.32) that replaces device plugins for GPU scheduling. In OpenShift 4.17+:

* **ResourceClaim**: A pod-level request for a specific GPU resource
* **ResourceClaimTemplate**: Reusable templates for common GPU configurations
* **DeviceClass**: Cluster-level definitions of available device types

DRA provides richer scheduling semantics than the traditional device plugin approach, including support for structured parameters and multi-device allocation.

[IMPORTANT]
====
DRA support in RHOAI is under active development. Check the https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.5[RHOAI 3.5 release notes] for the latest support status.

== Conceptual Section: llm-d Serving Topologies and the EPP Scheduler

[NOTE]
====
This section is conceptual. The lab cluster does not have GPUs, so you will understand the llm-d serving stack -- not deploy it. It summarizes the serving topologies, the EPP scheduler, and the autoscaling approaches that matter for operations planning of large-scale model deployments.
====

=== What Is llm-d?

llm-d is the distributed LLM serving stack integrated into RHOAI for large-scale model deployments. It extends the https://gateway-api-inference-extension.sigs.k8s.io/[Gateway API Inference Extension^] with deeper vLLM runtime integration -- distributed and shared KV cache and disaggregated prefill -- and is one of the most advanced solutions currently available for large-scale LLM deployments.

The disaggregated serving approach combines three ingredients: an LLM-aware router, a distributed KV cache, and disaggregated prefill optimizations. Such a configuration makes the deployment more similar to an appliance than a traditional Kubernetes deployment -- it is designed for very large-scale deployments where few models are served in a single cluster.

llm-d is not the only project in this space: the most famous alternative is NVIDIA Dynamo, and the main difference is focus. NVIDIA Dynamo is specialized and deeply integrated with NVIDIA hardware, while llm-d aims to support different hardware and integrate existing open source projects, leveraging the ecosystem.

=== Deployment Topologies

==== Single-Node Deployment

The simplest topology. A single vLLM instance serves the model from one node.

* **Best for**: Models that fit in a single GPU's memory (7B--13B parameter models on A100-80GB)
* **Scaling**: Horizontal pod autoscaling adds replicas on separate nodes
* **Limitation**: Cannot serve models larger than single-node GPU memory

==== Multi-Node Data Parallelism (DP)

Multiple replicas of the full model run independently across nodes. A load balancer distributes requests.

* **Best for**: High-throughput inference with models that fit on a single node
* **Scaling**: Each replica handles requests independently
* **Trade-off**: No memory aggregation -- each node must hold the full model

==== Prefill/Decode Disaggregation (PD Disaggregation)

Separates the two phases of LLM inference into specialized worker pools:

* **Prefill workers**: Process the input prompt and produce the first token (compute-bound -- this phase impacts Time to First Token, TTFT)
* **Decode workers**: Generate output tokens one at a time (memory-bound -- this phase impacts Inter-Token Latency, ITL)

Given the different nature of the two workloads, disaggregated prefill lets you scale and tune each phase independently -- for example, a workload with long input prompts needs more prefill replicas. The main challenge is that prefill initializes the KV cache, so it must be transferred from the prefill instance to the decode instance to continue generation -- which requires the distributed KV cache and a routing component (see below). This topology was introduced by the Mooncake project and later adopted by NVIDIA Dynamo and llm-d.

This topology enables:

* Independent scaling of prefill and decode capacity
* Hardware optimization (high-bandwidth GPUs for prefill, lower-cost GPUs for decode)
* Reduced time-to-first-token (TTFT) under high load

==== WideEP (Wide Expert Parallelism)

For Mixture-of-Experts (MoE) models like Mixtral, WideEP distributes expert layers across nodes:

* **Expert parallelism**: Different experts run on different GPUs/nodes
* **All-to-all communication**: Tokens are routed to the appropriate expert via high-speed interconnect
* **Best for**: MoE models where expert layers exceed single-node memory

=== Endpoint Picker Pod (EPP)

Intelligent routing in llm-d deployments builds on the Gateway API Inference Extension. Envoy proxy is the core component: its https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/ext_proc_filter[External Processing (ext_proc)^] filter defines a gRPC protocol that external services implement to read and modify both HTTP headers and the request body during processing.

The Gateway API Inference Extension adopts this concept to define the **Endpoint Picker protocol (EPP)**. An Endpoint Picker picks an endpoint from the https://gateway-api-inference-extension.sigs.k8s.io/concepts/api_types/[InferencePool^], and every implementation must support the Envoy External Processing protocol so the Envoy proxy can invoke it during request processing.

The EPP is the intelligent request router:

* **KV-cache-aware routing**: Directs requests to the replica most likely to have relevant KV cache entries, reducing redundant computation
* **Load-aware scheduling**: Considers GPU memory utilization, queue depth, and active request count
* **Session affinity**: Multi-turn conversations route to the same replica for cache reuse
* **Health monitoring**: Removes unhealthy replicas from the routing pool

One of the most interesting implementations is llm-d's **inference-scheduler**. It supports different filters and scoring logic -- for example, it can scrape metrics from the vLLM instances and use the `vllm:num_requests_waiting` metric to pick the replica with the lowest number of waiting requests.

From a Kubernetes perspective, each Endpoint Picker is a separate deployment, usually in the same namespace as the model (not required). The requirements: access to the vLLM container to collect metrics, and gateway (Envoy) reachability to the Endpoint Picker. Communication can be secured via mTLS.

=== KServe LLMInferenceService

The configuration of InferencePools, InferenceModels, and Endpoint Pickers becomes complex for production deployments. KServe's `LLMInferenceService` API simplifies this with a higher-level abstraction that automatically manages the underlying gateway components. `LLMInferenceServiceConfig` acts as a preset template encapsulating common configuration patterns -- intelligent routing, KV-cache-aware scheduling, and disaggregated serving -- hiding the low-level complexity while still allowing customization when needed.

[cols="1,1,1"]
|===
|Aspect |InferenceService + ServingRuntime |LLMInferenceService + LLMInferenceServiceConfig

|Primary use case
|Predictive AI (classification, regression)
|Generative AI (LLMs, text generation)

|Deployment patterns
|Single-node, simple scaling
|Multinode distributed inference, disaggregated serving

|Configuration template
|ServingRuntime defines a model server template
|LLMInferenceServiceConfig defines base LLM config with inheritance

|Routing and scheduling
|Basic load balancing
|Advanced routing with gateway, scheduler, and KV-cache-aware scheduling
|===

=== Distributed KV Cache

The KV cache is a critical aspect of efficient LLM execution. The intuition behind the **distributed KV cache**: store KV blocks in an external cache and reuse them when necessary. Two main benefits:

* The KV cache instance size is no longer limited by the available memory
* Blocks can be shared across different replicas

The optimization only pays off if the time to transfer KV cache data from one instance to another is very fast -- in the range of milliseconds. Two projects were created specifically for this focus: **LMCache** ("Redis for LLMs" -- an API to cache KV blocks; the main benefit applies to scenarios with very long input prompts, as in RAG, so prefill does not need to be performed for every new request) and **NVIDIA Inference Xfer Library (NIXL)** -- a small library accelerating point-to-point communication for AI runtimes, providing an abstraction over different types of memory (GPU and CPU) and storage. NIXL is flexible enough to be used even without disaggregated serving -- for example, leveraging CPU memory as an extension of GPU memory for a larger KV cache.

The distribution of the KV cache affects the router too: even when the cache is accessible by all replicas, it is more efficient to forward a request to a replica where the necessary KV cache blocks are already ready -- avoiding a cache miss and a block transfer.

=== Network Requirements

Everything described so far is applicable to a traditional Kubernetes cluster that has at least one node with GPUs -- but that is not enough to support disaggregated serving. As soon as the runtime is distributed, and in particular the KV cache is shared across different deployments, the network bandwidth available to share the KV cache blocks becomes critical and a **dedicated network configuration is required**.

The traditional pod network interface is usually backed by an Ethernet connection with up to 10--20 Gbps, while the bandwidth requirement is about one order of magnitude higher -- around 500--600 Gbps:

* **NVLink / NVSwitch** (NVIDIA): multiple GPUs connected to break the Tbps limit in some configurations
* **RDMA / RoCE** (RDMA over Converged Ethernet): up to 800 Gbps, not specific to NVIDIA hardware
* **InfiniBand**: the classic HPC RDMA implementation, now becoming more widely adopted with the evolution of generative AI workloads

=== Workload Variant Autoscaler (WVA)

llm-d's **Workload Variant Autoscaler (WVA)** is designed specifically for LLM workloads. Instead of just monitoring CPU or request counts, WVA looks at what each pod can handle, considers that different requests require different amounts of work (some generate many tokens, others just a few), and scales based on your actual latency targets. This lets the cluster run at higher utilization before adding pods, while still meeting performance goals.

Disaggregated prefill autoscaling differs significantly from traditional Kubernetes autoscaler definitions: it functions more like a *runtime controller* that observes system status and automatically rebalances replica roles or adjusts replica counts for each role (prefill vs decode).

=== Batch Inference

llm-d supports batch inference for processing large datasets:

* **Offline batch jobs**: Submit a file of prompts and receive a file of completions
* **Priority scheduling**: Batch jobs run at lower priority than real-time serving
* **Integration**: Works with Kueue for GPU quota management

=== Flow Control and Autoscaling

[cols="1,3"]
|===
|Mechanism |Description

|**Request queuing**
|EPP queues requests when all replicas are at capacity, with configurable queue depth and timeout

|**Token-level throttling**
|Rate limiting based on tokens-per-second rather than requests-per-second

|**KPA (Knative Pod Autoscaler)**
|Scales replicas based on concurrency or RPS targets

|**HPA with custom metrics**
|Scales based on GPU utilization, queue depth, or KV cache pressure via Prometheus metrics

|**WVA (Workload Variant Autoscaler)**
|llm-d's autoscaler: scales on actual latency targets, considering the work each request requires

|**Scale-to-zero**
|Supported with Knative Serving; cold start adds latency for first request
|===

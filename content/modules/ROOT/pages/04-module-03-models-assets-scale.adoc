== Conceptual Section: Kueue GPU Scheduling

[NOTE]
====

=== What Is Kueue?

Kueue is a Kubernetes-native job queuing system that manages resource quotas and fair scheduling for batch workloads. In RHOAI, Kueue is essential for managing GPU access across teams and projects.

Kueue operates through four key CRDs:

[cols="1,3"]
|===
|CRD |Purpose

|**ResourceFlavor**
|Defines a type of resource (e.g., `nvidia-a100-40gb`, `nvidia-l4`, `cpu-only`). Maps to node labels so Kueue knows which nodes provide which hardware.

|**ClusterQueue**
|A cluster-scoped queue that defines resource quotas. Specifies how many resources of each flavor are available and borrowing limits.

|**LocalQueue**
|A namespace-scoped queue that points to a ClusterQueue. Users submit workloads to a LocalQueue; Kueue routes them to the backing ClusterQueue.

|**Cohort**
|A logical grouping of ClusterQueues that can borrow resources from each other. Enables cross-team resource sharing with guaranteed minimums.
|===

=== Inspect Kueue Installation

Check whether the Kueue operator is installed:

[source,bash,role="execute"]
----
oc get csv -A | grep kueue
----

List any existing Kueue CRDs:

[source,bash,role="execute"]
----
oc get crd | grep kueue
----

Expected CRDs include:

[source,text]
----

localqueues.kueue.x-k8s.io
resourceflavors.kueue.x-k8s.io
workloads.kueue.x-k8s.io
----

=== Example: ResourceFlavor for GPU Nodes

On a GPU-equipped cluster, a ResourceFlavor would look like this:

[source,yaml]
----
apiVersion: kueue.x-k8s.io/v1beta1
kind: ResourceFlavor
metadata:
  name: nvidia-a100-40gb
spec:
  nodeLabels:
    nvidia.com/gpu.product: "NVIDIA-A100-SXM4-40GB"
  tolerations:
    - key: nvidia.com/gpu
      operator: Exists
      effect: NoSchedule
----

=== Example: ClusterQueue with Quotas and Borrowing

A ClusterQueue defines the total resources available and the borrowing policy:

[source,yaml]
----
apiVersion: kueue.x-k8s.io/v1beta1
kind: ClusterQueue
metadata:
  name: data-science-team
spec:
  cohort: "research-department"        # <1>
  resourceGroups:
    - coveredResources: ["cpu", "memory", "nvidia.com/gpu"]
      flavors:
        - name: nvidia-a100-40gb
          resources:
            - name: "nvidia.com/gpu"
              nominalQuota: 4           # <2>
              borrowingLimit: 2          # <3>
            - name: "cpu"
              nominalQuota: 32
            - name: "memory"
              nominalQuota: 128Gi
  preemption:
    withinClusterQueue: LowerPriority
    reclaimWithinCohort: Any
----
<1> Cohort membership enables borrowing from other ClusterQueues in the same cohort
<2> Guaranteed quota: 4 GPUs always available to this team
<3> Can borrow up to 2 additional GPUs from the cohort when other teams have idle resources

=== Example: LocalQueue in a User Namespace

Users interact with LocalQueues, not ClusterQueues:

[source,yaml]
----
apiVersion: kueue.x-k8s.io/v1beta1
kind: LocalQueue
metadata:
  name: team-queue
  namespace: ds-project-alpha
spec:
  clusterQueue: data-science-team
----

== Conceptual Section: MIG, Dynamic MIG, and DRA

[NOTE]
====
This section describes GPU partitioning technologies. These concepts are important for planning RHOAI deployments but cannot be demonstrated on a CPU-only cluster.
====

=== Multi-Instance GPU (MIG)

NVIDIA Multi-Instance GPU (MIG) allows a single physical GPU to be partitioned into up to seven isolated instances, each with its own memory, cache, and compute resources.

[cols="1,2,2"]
|===
|MIG Profile |GPU Memory |Use Case

|`1g.5gb`
|5 GB
|Small inference workloads, notebook exploration

|`2g.10gb`
|10 GB
|Medium model training, batch inference

|`3g.20gb`
|20 GB
|Large model fine-tuning

|`4g.20gb`
|20 GB
|Higher compute, same memory as 3g

|`7g.40gb`
|40 GB (full GPU)
|Full GPU for largest workloads
|===

MIG provides hardware-level isolation -- each instance has guaranteed memory bandwidth and compute, unlike time-slicing which shares resources.

=== Dynamic MIG

Dynamic MIG (available through the NVIDIA GPU Operator) enables on-the-fly reconfiguration of MIG partitions based on workload demand. Key benefits:

* **Automatic partitioning**: The GPU Operator watches for pod resource requests and reconfigures MIG profiles to match
* **No node drain required**: Partitions are adjusted without evicting existing workloads (when possible)
* **Strategy-based**: Administrators define a `MIGStrategy` (e.g., `mixed` or `single`) on the ClusterPolicy

=== Dynamic Resource Allocation (DRA)

DRA is a Kubernetes-native mechanism (GA in Kubernetes 1.32) that replaces device plugins for GPU scheduling. In OpenShift 4.17+:

* **ResourceClaim**: A pod-level request for a specific GPU resource
* **ResourceClaimTemplate**: Reusable templates for common GPU configurations
* **DeviceClass**: Cluster-level definitions of available device types

DRA provides richer scheduling semantics than the traditional device plugin approach, including support for structured parameters and multi-device allocation.

[IMPORTANT]
====
DRA support in RHOAI is under active development. Check the https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.5[RHOAI 3.5 release notes] for the latest support status.
====

== Conceptual Section: llm-d Serving Topologies and the EPP Scheduler

llm-d (formerly vLLM-d) is the distributed LLM serving stack integrated into RHOAI for large-scale model deployments. Understanding its deployment topologies is critical for operations planning.

=== Deployment Topologies

==== Single-Node Deployment

The simplest topology. A single vLLM instance serves the model from one node.

* **Best for**: Models that fit in a single GPU's memory (7B--13B parameter models on A100-80GB)
* **Scaling**: Horizontal pod autoscaling adds replicas on separate nodes
* **Limitation**: Cannot serve models larger than single-node GPU memory

==== Multi-Node Data Parallelism (DP)

Multiple replicas of the full model run independently across nodes. A load balancer distributes requests.

* **Best for**: High-throughput inference with models that fit on a single node
* **Scaling**: Each replica handles requests independently
* **Trade-off**: No memory aggregation -- each node must hold the full model

==== Prefill/Decode Disaggregation (PD Disaggregation)

Separates the two phases of LLM inference into specialized worker pools:

* **Prefill workers**: Process the input prompt (compute-intensive, high memory bandwidth)
* **Decode workers**: Generate output tokens one at a time (latency-sensitive, lower compute)

This topology enables:

* Independent scaling of prefill and decode capacity
* Hardware optimization (high-bandwidth GPUs for prefill, lower-cost GPUs for decode)
* Reduced time-to-first-token (TTFT) under high load

==== WideEP (Wide Expert Parallelism)

For Mixture-of-Experts (MoE) models like Mixtral, WideEP distributes expert layers across nodes:

* **Expert parallelism**: Different experts run on different GPUs/nodes
* **All-to-all communication**: Tokens are routed to the appropriate expert via high-speed interconnect
* **Best for**: MoE models where expert layers exceed single-node memory

=== Endpoint Picker Pod (EPP)

The EPP is the intelligent request router in llm-d deployments:

* **KV-cache-aware routing**: Directs requests to the replica most likely to have relevant KV cache entries, reducing redundant computation
* **Load-aware scheduling**: Considers GPU memory utilization, queue depth, and active request count
* **Session affinity**: Multi-turn conversations route to the same replica for cache reuse
* **Health monitoring**: Removes unhealthy replicas from the routing pool

=== Batch Inference

llm-d supports batch inference for processing large datasets:

* **Offline batch jobs**: Submit a file of prompts and receive a file of completions
* **Priority scheduling**: Batch jobs run at lower priority than real-time serving
* **Integration**: Works with Kueue for GPU quota management

=== Flow Control and Autoscaling

[cols="1,3"]
|===
|Mechanism |Description

|**Request queuing**
|EPP queues requests when all replicas are at capacity, with configurable queue depth and timeout

|**Token-level throttling**
|Rate limiting based on tokens-per-second rather than requests-per-second

|**KPA (Knative Pod Autoscaler)**
|Scales replicas based on concurrency or RPS targets

|**HPA with custom metrics**
|Scales based on GPU utilization, queue depth, or KV cache pressure via Prometheus metrics

|**Scale-to-zero**
|Supported with Knative Serving; cold start adds latency for first request
|===

== The Data Stewardship Organization Model

Enterprises do not organize their data science platform around job titles -- they organize it around *lines of business* and the people accountable for their data. Assume an organization that is organized around data stewardship, where a line of business has data owners. This is what we want to model when configuring the platform:

* A *line of business* (LOB) -- for example Lending or Insurance -- owns a portfolio of data assets and the models built from them.
* *Data owners* are accountable for the LOB's data. They approve access, govern the project, and answer for how the data is used.
* *Data stewards* implement that governance day to day. They curate data products, manage quality, and prepare data for the scientists.
* *Data scientists* consume the governed data, build and train models, and iterate in workbenches.
* *ML engineers* operate the platform layer -- serving runtimes, pipelines, monitoring -- across lines of business.

The mapping from the organization to the platform is direct:

[cols="2,2,3",options="header"]
|===
|Organization |Platform Object |Mechanism

|Line of business
|Data Science Project (namespace)
|One namespace per LOB: `rhoai-lending`, `rhoai-insurance`

|Persona (owner, steward, scientist)
|OpenShift group per LOB persona
|From the directory: `lending-data-owners`, `lending-data-stewards`, ...

|Accountability level
|RoleBinding in the LOB project
|`admin` for owners, `edit` for stewards and scientists; no bindings for other LOBs

|Fine-grained notebook access
|Custom workbench roles
|ClusterRoles labeled `opendatahub.io/role-type: workbench`

|Who may use RHOAI at all
|RHOAI Auth CR
|`adminGroups` / `allowedGroups`
|===

The identity flow that makes this work:

. The OCP-native LDAP identity provider authenticates the persona directly against the FreeIPA directory and *claims* a username (the platform admin continues to auth via the Keycloak IdP).
. The username lands in *OpenShift groups*, carried by the groups from the directory.
. Groups are bound to roles in namespaces via *RoleBindings*.
. RHOAI surfaces read the same groups: the *Auth CR* gates dashboard access, and the dashboard lists exactly the projects the user's groups can see.

[IMPORTANT]
====
Authentication is OpenShift's job -- RHOAI never has its own user store. Every access decision in the dashboard resolves to an OpenShift group and an OpenShift RoleBinding. Get the groups right and the platform follows.
====

== Exercise 2: Configure the RHOAI Auth CR

The RHOAI Auth CR (`services.platform.opendatahub.io`) controls which groups can access the RHOAI dashboard, and at what level. The manifest lives in the workshop's GitOps repository:

[source,bash,role="execute"]
----
cat manifests/02-idp-users-groups/rhoai-auth/auth-config.yaml
----

Review the key fields:

[source,yaml]
----
apiVersion: services.platform.opendatahub.io/v1alpha1
kind: Auth                              # <1>
metadata:
  name: auth                            # <2>
  namespace: redhat-ods-applications
spec:
  adminGroups:                          # <3>
    - rhods-admins
  allowedGroups:                        # <4>
    - rhods-users
----
<1> *Auth CR* -- the RHOAI authorization object; `kind: Auth` from `services.platform.opendatahub.io`.
<2> *Singleton* -- the CRD requires the name to be exactly `auth`; the operator creates it on install and this apply adopts the existing CR.
<3> *Admin groups* -- can administer RHOAI settings: serving runtimes, cluster settings, accelerator profiles.
<4> *Allowed groups* -- can access the RHOAI dashboard at all.

[source,bash,role="execute"]
----
oc apply -f manifests/02-idp-users-groups/rhoai-auth/auth-config.yaml
----

[NOTE]
====
Users not in `allowedGroups` will see an "Access denied" page.
====

Every data owner, steward, and scientist is a member of `rhods-users`, so they can all reach the dashboard -- what they can do once inside is decided by the RoleBindings in the next exercise. The one persona outside `rhods-users` -- `dev-nia`, the developer -- cannot reach the dashboard at all; that is the denial path you prove in Exercise 5.

=== Verify

== Exercise 3: Line-of-Business Projects and RoleBindings

Create one Data Science Project per line of business, label it so it appears in the RHOAI dashboard, and bind roles per persona:

[source,bash,role="execute"]
----
for lob in lending insurance; do
  oc new-project rhoai-${lob}
  oc label namespace rhoai-${lob} opendatahub.io/dashboard="true" --overwrite
  oc adm policy add-role-to-group admin ${lob}-data-owners -n rhoai-${lob}
  oc adm policy add-role-to-group edit ${lob}-data-stewards -n rhoai-${lob}
  oc adm policy add-role-to-group edit ${lob}-data-scientists -n rhoai-${lob}
done
----

[IMPORTANT]
====
The `opendatahub.io/dashboard: "true"` label is what makes a namespace show up in the RHOAI dashboard as a *Data Science Project* -- a bare `oc new-project` namespace is invisible to it. Projects created from the dashboard get the label automatically; namespaces created from the CLI do not, so label them explicitly.
====

[CAUTION]
====
We deliberately do *not* bind `view` to `rhods-users` in the line-of-business projects, even though read-only access for everyone sounds right. A known RHOAI behavior lets a user with the `view` role on a project open -- and run -- workbenches from the dashboard, even though `view` is read-only at the API level. Grant visibility case by case to individual users or groups, never to the whole `rhods-users` group.
====

[NOTE]
====
RoleBindings are namespace-scoped, so this is where line-of-business isolation comes from: `sci-eve` has `edit` in `rhoai-lending` and no role at all in `rhoai-insurance` -- the project is not even listed for her in the dashboard.
====

== Exercise 4: Least-Privilege Workbench Roles

Custom workbench roles provide finer-grained access control within data science projects. These are `ClusterRoles` labeled for the RHOAI dashboard, bound at the namespace level. The manifest lives in the GitOps repository:

[source,bash,role="execute"]
----
cat manifests/02-idp-users-groups/rhoai-auth/workbench-roles.yaml
----

Review the key fields of the `workbench-maintainer` role -- the other three follow the same shape:

[source,yaml]
----
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: workbench-maintainer
  labels:
    opendatahub.io/dashboard: "true"       # <1>
    opendatahub.io/role-type: "workbench"  # <2>
rules:
  - apiGroups: ["kubeflow.org"]
    resources: ["notebooks"]               # <3>
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  - apiGroups: [""]
    resources: ["persistentvolumeclaims"]  # <4>
    verbs: ["get", "list", "watch", "create", "delete"]
----
<1> *Dashboard label* -- exposes the role to the RHOAI dashboard.
<2> *Role type* -- marks this as a workbench-scoped role.
<3> *Notebook resources* -- the `kubeflow.org` Notebook CR is the workbench; maintainers get the full lifecycle.
<4> *Storage access* -- maintainers can create and delete the PVCs behind workbenches.

[source,bash,role="execute"]
----
oc apply -f manifests/02-idp-users-groups/rhoai-auth/workbench-roles.yaml
----

Now bind the workbench roles per persona, in each line-of-business project:

[source,bash,role="execute"]
----
for lob in lending insurance; do
  oc adm policy add-role-to-group workbench-maintainer ${lob}-data-owners -n rhoai-${lob}
  oc adm policy add-role-to-group workbench-editor ${lob}-data-stewards -n rhoai-${lob}
  oc adm policy add-role-to-group workbench-operator ${lob}-data-scientists -n rhoai-${lob}
done
----

[NOTE]
====
The persona-to-workbench-role mapping follows accountability: data owners maintain the full workbench lifecycle, data stewards edit workbench configuration, and data scientists create and operate workbenches (start, stop, update) without deleting them or the storage behind them.
====

=== Verify

[source,bash,role="execute"]
----
oc get clusterroles -l opendatahub.io/role-type=workbench -o custom-columns=NAME:.metadata.name
----

Expected output:

----
NAME

workbench-maintainer
workbench-operator
workbench-reader

== Exercise 5: Prove the Model -- Persona Access Walkthrough

Everything so far is configuration. This exercise verifies the RBAC decisions as the personas themselves, using `oc auth can-i` impersonation -- no credential switching required. Impersonate the persona *and* their groups: groups are claimed at authentication, and impersonation does not run it, so every decision must ride the persona's groups along with `--as-group`.

[IMPORTANT]
====
`--as` alone impersonates a groupless user -- group-bound RoleBindings only apply when the groups ride along with `--as-group`. Without them, every decision returns `no`, including the ones that should be `yes` -- even for a data owner with `admin`. This is the single most common impersonation mistake.
====

----

== Exercise 6: MaaS Permissions -- Performance Tiers Bound to Groups

The Lending line of business has published its model: `qwen25-05b`, a modelcar served as an `LLMInferenceService` wired to the MaaS gateway. The data owner decides who gets access to the LOB's model and at what tier. In MaaS, a performance tier *is* a subscription: there is no `performanceTier` field -- the tier is a `MaaSSubscription` bound to groups, with a tier-appropriate token budget.

[cols="1,2,2,1,1",options="header"]
|===
|Tier |Subscription |Bound groups |Token limits |Priority

|Performance
|`lending-performance-tier`
|lending-data-owners, lending-data-stewards
|100000 / 1m
|1

|Standard
|`lending-standard-tier`
|lending-data-scientists
|10000 / 1m
|0
|===

Both tiers attribute usage to `costCenter: lending` -- metering per line of business, so the data owner can answer for the LOB's model spend.

The governance manifests you apply by hand stay in `manifests/02-idp-users-groups/maas/`:

=== 2 Create the tier subscriptions and auth policies

Three objects work together per tier. The `MaaSSubscription` binds the tier to groups and sets the token budget. The `MaaSAuthPolicy` admits exactly those groups at the gateway. The `MaaSModelRef` (already applied) publishes the model.

[source,bash,role="execute"]
----
ls manifests/02-idp-users-groups/maas/
----

Review the performance-tier subscription:

[source,yaml]
----
apiVersion: maas.opendatahub.io/v1alpha1
kind: MaaSSubscription
metadata:
  name: lending-performance-tier
  namespace: models-as-a-service        # <1>
spec:
  owner:
    groups:                             # <2>
      - name: lending-data-owners
      - name: lending-data-stewards
  priority: 1                           # <3>
  tokenMetadata:
    costCenter: lending                 # <4>
    organizationId: lending
  modelRefs:
    - name: qwen25-05b-maas
      namespace: rhoai-lending
      tokenRateLimits:
        - limit: 100000
          window: 1m                    # <5>
----
<1> *Tenant namespace* -- must be `models-as-a-service`, the only namespace `maas-api` reads subscriptions from; anywhere else the subscription is silently ignored.
<2> *Bound groups* -- the tier IS the subscription: these groups hold the performance tier.
<3> *Priority* -- wins when a user holds multiple subscriptions.
<4> *Cost center* -- usage attribution per line of business, the stewardship story.
<5> *Token budget* -- 100 000 tokens per minute for this tier.

And the auth policy that admits those groups at the gateway:

[source,yaml]
----
apiVersion: maas.opendatahub.io/v1alpha1
kind: MaaSAuthPolicy
metadata:
  name: lending-performance-tier-auth
  namespace: models-as-a-service
spec:
  subjects:
    groups:                             # <1>
      - name: lending-data-owners
      - name: lending-data-stewards
  modelRefs:                            # <2>
    - name: qwen25-05b-maas
      namespace: rhoai-lending
----
<1> *Subjects* -- must match the subscription's `owner.groups`; a key minted by a user outside these groups gets 403 at call time.
<2> *Model refs* -- the published models this policy protects.

The standard tier is identical in shape, bound to `lending-data-scientists` at 10 000 tokens per minute. Apply all four manifests:

[source,bash,role="execute"]
----

oc apply -f manifests/02-idp-users-groups/maas/subscription-standard.yaml
oc apply -f manifests/02-idp-users-groups/maas/authpolicy-performance.yaml
oc apply -f manifests/02-idp-users-groups/maas/authpolicy-standard.yaml
----

=== 3 Mint API keys as the personas

API keys bind to a subscription -- the tier. Log in as the lending data scientist and mint two keys, one against each tier:

[source,bash,role="execute",subs="attributes"]
----
oc login -u sci-eve -p {password} {openshift_api_url}

CLUSTER_DOMAIN=$(oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}')
export HOST="https://maas.${CLUSTER_DOMAIN}"

# Against the performance tier -- sci-eve is not in its groups...
curl -sSk -X POST "${HOST}/maas-api/v1/api-keys" \
  -H "Authorization: Bearer $(oc whoami -t)" \
  -H "Content-Type: application/json" \
  -d '{"name":"sci-eve-perf","expiresIn":"1h","subscription":"lending-performance-tier"}' \
  | jq -r .key > /tmp/sci-eve-perf.key

# ...and against the standard tier -- the tier her groups do hold
export SCI_EVE_KEY=$(curl -sSk -X POST "${HOST}/maas-api/v1/api-keys" \
  -H "Authorization: Bearer $(oc whoami -t)" \
  -H "Content-Type: application/json" \
  -d '{"name":"sci-eve-standard","expiresIn":"1h","subscription":"lending-standard-tier"}' \
  | jq -r .key)
echo "Standard key: ${SCI_EVE_KEY:0:12}..."
----

Now the data owner, for the performance tier:

[source,bash,role="execute",subs="attributes"]
----
oc login -u own-alice -p {password} {openshift_api_url}

export ALICE_KEY=$(curl -sSk -X POST "${HOST}/maas-api/v1/api-keys" \
  -H "Authorization: Bearer $(oc whoami -t)" \

oc login -u {user} -p {password} {openshift_api_url}

=== 4 Prove tier-bound group enforcement

Call the model with each key. Body-based routing needs the full catalog id, `publishers/rhoai-lending/models/qwen25-05b`:

[source,bash,role="execute"]
----
MODEL_ID="publishers/rhoai-lending/models/qwen25-05b"

# The data owner's performance-tier key -- admitted, her groups are in the tier
curl -sSk "${HOST}/v1/chat/completions" \
  -H "Authorization: Bearer ${ALICE_KEY}" \
  -H "Content-Type: application/json" \
  -d "{\"model\":\"${MODEL_ID}\",\"messages\":[{\"role\":\"user\",\"content\":\"Hello\"}],\"max_tokens\":20}" \
  | jq -r '.choices[0].message.content'

# The data scientist's performance-tier key -- rejected: her groups are not in the tier
curl -sSk "${HOST}/v1/chat/completions" \
  -H "Authorization: Bearer $(cat /tmp/sci-eve-perf.key)" \
  -H "Content-Type: application/json" \
  -d "{\"model\":\"${MODEL_ID}\",\"messages\":[{\"role\":\"user\",\"content\":\"Hello\"}],\"max_tokens\":20}" \
  | jq -r '.error // .choices[0].message.content'

# The data scientist's standard-tier key -- admitted at the lower budget
curl -sSk "${HOST}/v1/chat/completions" \
  -H "Authorization: Bearer ${SCI_EVE_KEY}" \
  -H "Content-Type: application/json" \
  -d "{\"model\":\"${MODEL_ID}\",\"messages\":[{\"role\":\"user\",\"content\":\"Hello\"}],\"max_tokens\":20}" \
  | jq -r '.choices[0].message.content'
----

Expected results:

* The owner's performance-tier key returns a completion.
* The scientist's performance-tier key returns an authorization error -- the tier's `MaaSAuthPolicy` admits only its bound groups, enforced at the gateway before the model is ever reached.
* The scientist's standard-tier key returns a completion, at 10 000 tokens per minute instead of 100 000.

[NOTE]
====
This is the data owner's lever in practice: grant a tier by adding a group to the subscription and its auth policy, revoke it by removing the group. The tier budget and the `costCenter` attribution make the model spend auditable per line of business.

== Reference: RHOAI RBAC Surface Area

RHOAI RBAC spans multiple subsystems, each with its own authorization model. This is where access control and identity come into play: every surface reads the OpenShift groups from your identity provider. The following table is a comprehensive reference for the RBAC surfaces a platform administrator must understand and configure.

[cols="2,2,3,2",options="header"]
|===
|Subsystem |Resource Type |RBAC Mechanism |Key Groups/Roles

|*RHOAI Dashboard*
|Dashboard access, settings
|Auth CR (`adminGroups`, `allowedGroups`)
|`rhods-admins`, `rhods-users`

|*Data Science Projects*
|Namespaces, workbenches, pipelines
|OpenShift RBAC (`RoleBinding` in namespace)
|`admin`, `edit` ClusterRoles; avoid `view` -- the dashboard lets `view` users open workbenches (see Exercise 3)

|*Workbenches (Notebooks)*
|Notebook CR lifecycle
|Custom ClusterRoles with `opendatahub.io/role-type` label
|`workbench-maintainer`, `workbench-reader`, `workbench-operator`, `workbench-editor`

|*Model Serving (KServe)*
|InferenceService, ServingRuntime
|OpenShift RBAC in serving namespace
|`admin`, `edit` for create/update; `view` for read-only

|*Model Serving (ModelMesh)*
|InferenceService, ServingRuntime
|OpenShift RBAC in serving namespace
|Same as KServe; namespace-scoped

|*Model Registry*
|RegisteredModel, ModelVersion, ModelArtifact
|Model Registry RBAC (namespace-scoped)
|Tied to namespace `RoleBinding`; no separate auth model

|*MaaS (Models-as-a-Service)*
|MaaSSubscription, MaaSAuthPolicy, API keys
|Performance tiers bound to groups (`owner.groups`, `subjects.groups`) + per-tier token rate limits
|Tier subscriptions per persona group; `costCenter` for line-of-business metering

|*Pipelines (Data Science Pipelines)*
|PipelineRun, Pipeline definitions
|OpenShift RBAC + DSP namespace access
|`admin`/`edit` for pipeline creation; `view` for run monitoring

|*Distributed Workloads (Kueue)*
|ClusterQueue, LocalQueue, Workload
|Kueue RBAC (ClusterRole for queue admin)
|Cluster-scoped for ClusterQueue; namespace-scoped for LocalQueue/Workload

|*TrustyAI*
|TrustyAIService, bias/explainability data
|OpenShift RBAC in TrustyAI namespace
|`admin`/`edit` for configuration; `view` for dashboard access

|*Model Monitoring*
|ModelMonitor, metrics endpoints
|OpenShift RBAC + Prometheus RBAC
|`monitoring-edit` for alert rules; `view` for dashboard access

|*Custom Serving Runtimes*
|ServingRuntime (cluster-scoped)
|Cluster admin or delegated ClusterRole
|Typically restricted to `rhods-admins`; runtime selection available to project `edit` role
|===

=== Mapping the Personas onto the Surfaces

For the data-stewardship organization modeled in this module, the personas resolve against those surfaces as follows:

[cols="2,3,3",options="header"]
|===
|Persona |Within their line of business |Platform-wide

|*Data Owner*
|`admin` on the LOB project: governs RBAC, approves access, full workbench lifecycle (`workbench-maintainer`), serves models
|RHOAI dashboard user; owns the project wherever it is shared

|*Data Steward*
|`edit` on the LOB project: curates data and features, edits workbench configuration (`workbench-editor`), runs pipelines
|RHOAI dashboard user

|*Data Scientist*
|`edit` on the LOB project: builds in workbenches (`workbench-operator`), trains models, monitors runs
|RHOAI dashboard user; other LOBs are invisible -- no bindings

|*ML Engineer*
|`edit` in serving and platform namespaces: operates serving runtimes, monitoring, pipelines
|No RHOAI admin rights unless granted

|*Platform Admin*
|All of the above, everywhere
|Auth CR `adminGroups`: manages serving runtimes, cluster settings, accelerator profiles
|===

The pattern to take away: *the identity provider produces the user, the directory produces the groups, RoleBindings decide the namespace, the Auth CR decides the dashboard, and the subscription tier decides the model.* Every row in the subsystem table resolves to one of those five mechanisms.

[CAUTION]
====
This table covers the primary RBAC surfaces as of RHOAI 3.5. Additional subsystems (guardrails, evaluation hub) are in Technology Preview and may introduce their own authorization models. Always consult the https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.5[RHOAI 3.5 documentation^] for the latest RBAC guidance.
====

[WARNING]
====
The `cluster-admin` ClusterRole bypasses all RBAC checks. Avoid granting it to data science users. Instead, use the minimum set of roles described above to implement least-privilege access.
====
